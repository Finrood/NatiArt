## Current findings

### CA1. Expired/malformed directory JWTs escape the filter as server failures — OPEN (High)
- **Where:** `backend/directory-service/src/main/java/com/saas/directory/configuration/UserAuthenticationProvider.java:135-187`, `configuration/JwtAuthFilter.java:42-57`; product-service `configuration/JwtAuthFilter.java:68-84`.
- **Trigger / impact:** `decodeJWT()` calls the Auth0 verifier before the database check. Expiration, malformed input and invalid signatures throw unchecked `JWTVerificationException` subclasses, while the directory filter catches only `IllegalAccessException` as 401 and explicitly rethrows other runtime exceptions. MVC advice cannot handle an exception thrown before the controller. Thus normal access-token expiry follows a server-error path; product-service treats directory responses outside 401/403 as unavailable (503), so the storefront's 401-based refresh flow is not triggered reliably. Existing filter tests that mock only `IllegalAccessException` miss the real verifier failure.
- **Fix:** catch `JWTVerificationException` at the directory authentication boundary and map it to the same static 401 denial used for invalid persisted tokens. Keep database/infrastructure failures distinct; do not convert every runtime failure to 401. Handle a missing token explicitly in `/validate-token` as well.
- **Acceptance:** use the real verifier with synthetic signed expired tokens, bad signatures and malformed strings through the directory filter chain; each must return 401 without credential disclosure. A product protected request with an expired token must receive 401 and permit the normal browser refresh/retry. Simulated database outage must retain an infrastructure-error response.

### CA2. Directory throttling gives all product-service users one ten-request validation quota — OPEN (High)
- **Where:** directory-service `configuration/RateLimitFilter.java:26-38,64-66,101-112`; product-service `configuration/JwtAuthFilter.java:90-104`.
- **Trigger / impact:** `/validate-token` shares the login/registration limiter, keyed solely by the incoming socket IP with a default of ten requests/minute. Product-service forwards Authorization and a request ID, but no separate authenticated service identity. All cache misses from one product instance therefore debit the same directory bucket. Eleven distinct user tokens (or renewed validation after cache expiry) can exhaust it; directory 429 becomes product 503 for unrelated customers. The validation cache reduces calls but does not eliminate this shared ceiling.
- **Fix:** give authenticated internal token validation its own bounded service quota and trust boundary, separate from public login/registration buckets. Authenticate the service or enforce a documented private gateway policy; do not simply exempt a caller-supplied header or trust arbitrary forwarded IPs. Preserve limits on public token-validation probes and map overload consistently with Retry-After.
- **Acceptance:** requests for more than ten distinct users through one product-service address must work under the intended service quota; one user's login burst must not consume that quota. Untrusted callers must not bypass public limits by spoofing service/forwarded headers. Exercise both cold-cache and expired-cache traffic.

### CA3. Product-service cannot select constructors for four service beans — OPEN (High)
- **Where:** `backend/product-service/src/main/java/com/portcelana/natiart/service/AsaasPaymentService.java:64-104`, `service/ShippingService.java:48-68`, `configuration/DatabaseTokenValidationCache.java:35-59`, and `service/DatabaseRateLimitStore.java:20-27`.
- **Trigger / impact:** all four `@Service` classes have a public production constructor and an additional package-private test constructor, neither annotated `@Autowired`, and no no-argument constructor. Spring's implicit constructor injection applies to a single constructor; these beans cannot be instantiated through the normal application context. Mockito/direct-constructor tests do not verify that wiring.
- **Fix:** annotate the production constructors with `@Autowired`, exactly as `OrderManagerImpl` and directory `AsaasUserManager` already do under `agents/java-spring.md`. Keep the test constructors package-private. Add one narrowly scoped context wiring test, and a full local-H2 boot smoke check with dummy integration configuration and no external egress.
- **Verified execution:** a real local-H2 product boot fails with `BeanInstantiationException: DatabaseRateLimitStore: No default constructor found`; the existing unit/slice suite nevertheless passes.
- **Acceptance:** the real product application context starts, all four beans use their configured values and managed dependencies, and existing unit tests remain green.

### CA4. A fresh production directory database has no roles and cannot register users — OPEN (High)
- **Where:** `backend/directory-service/src/main/resources/application.properties:28-31`, `application-production.properties:8-9`, `data.sql:3-7`; `src/main/java/com/saas/directory/service/UserManager.java:71-76`.
- **Trigger / impact:** role rows are inserted only by the local-only `data.sql`. Production disables SQL initialization, and no application bootstrap creates `USER`/`ADMIN`. Hibernate creates empty tables. The first valid registration throws `RoleNotFoundException`, and there is no supported admin provisioning path in the repository.
- **Fix:** add an idempotent production-safe initializer or documented bootstrap SQL for the two non-secret role rows. Keep demonstration accounts and known password hashes local-only. Document a separate explicit first-admin provisioning procedure with unique credentials; do not re-enable the entire seed file in production.
- **Acceptance:** start against an empty production-shaped schema, provision roles twice without duplicates, and successfully register a normal user. Assert no seeded demo user is present.

### CA5. Asaas account provisioning can be lost permanently or create duplicate customers — OPEN (High)
- **Where:** directory-service `src/main/java/com/saas/directory/service/UserManager.java:75-83,98-101`, `listener/UserRegistrationListener.java:42-82`, `service/AsaasUserManager.java:54-74`, `dto/asaas/AsaasCustomerCreationRequest.java:30-40`, `model/ExternalUser.java:9-23`, `repository/ExternalUserRepository.java:13`.
- **Trigger / impact:** the local user commits before an in-memory async event creates the provider customer. Restart between commit and processing loses the event; exhausted retries only log. The 20-attempt exponential retry configuration can occupy a bounded async worker for roughly ten hours; sleeping retries do not provide durable recovery. A timeout after Asaas creates a customer retries another POST without a stable external reference/reconciliation step. Reprocessing can insert multiple external mappings because `(user, paymentProcessor)` is not unique, while reads expect one result. Affected accounts can log in but cannot reliably check out because their external customer ID is missing or ambiguous.
- **Fix:** persist a provisioning job/outbox row in the registration transaction; process it with durable retry status and next-attempt time. Use the local immutable user ID as the provider external reference and reconcile an ambiguous result before creating again, according to the verified provider contract. Add a unique `(user_id, payment_processor)` mapping with a duplicate-reconciliation rollout. Expose provisioning status/retry feedback to checkout rather than requiring users to re-register.
- **Acceptance:** crash after user commit, timeout after provider creation, duplicate job delivery and final provider rejection each leave a recoverable, inspectable state; a successful retry produces exactly one provider customer and one local mapping.

### CA6. Registration validates presence but accepts unusable profile data and weak passwords — OPEN (Medium)
- **Where:** directory-service `src/main/java/com/saas/directory/dto/UserRegistrationDto.java:9-12`, `dto/ProfileDto.java:10-39`, `service/ProfileManager.java:24-39`, `model/User.java:66-69`.
- **Trigger / impact:** the API accepts a one-character password and arbitrary nonblank CPF/CEP values. For example CPF `abc` passes `@NotBlank` and is then stripped to an empty string before persistence/provider provisioning. Profile text has no length bounds despite default varchar column limits. Browser validators can be bypassed by calling the API, leaving invalid accounts or database/provider errors after apparent signup success. Password length is measured in characters up to 255 despite BCrypt's byte-length constraint.
- **Fix:** define the server-side registration contract in request DTO validators and normalization helpers: validate CPF checksum after digit normalization, Brazilian CEP/state/phone formats as applicable, and field lengths consistent with storage/provider limits. Apply the chosen minimum password length on the backend and reject unsupported BCrypt byte lengths explicitly; mirror this contract in the frontend. Keep login validation compatible with already-existing passwords and avoid logging rejected values.
- **Acceptance:** direct HTTP signup with alphabetic CPF, invalid checksum/CEP, overlong text, insufficient password length and an over-limit multibyte password returns 400 before persistence or provider work; valid formatted and normalized inputs produce the same stored data.

### CA7. Order idempotency replay returns a detached lazy collection and fails DTO mapping — OPEN (High)
- **Where:** product-service `src/main/java/com/portcelana/natiart/service/OrderManagerImpl.java:100-120,129-137`, `repository/OrderRepository.java:17`, `controller/OrderController.java:28-29`, `dto/OrderDto.java:48-50`, `model/CustomerOrder.java` (`items` mapping).
- **Trigger / impact:** a retry finds an existing order through a repository method with no item fetch plan, returns the entity and then maps `items` in the controller with `open-in-view=false`. The transaction/session has ended, so replay can throw `LazyInitializationException` instead of returning the already-reserved order. Fresh creation tests use initialized in-memory collections and do not exercise the detached replay path.
- **Fix:** make the replay lookup fetch the order items and fields needed by `OrderItemDto.from`, or map to an immutable response DTO inside a dedicated read-only transaction. Apply the same path to the unique-key-race loser. Do not enable open-in-view.
- **Acceptance:** through real JPA and the controller, submit an order, clear the persistence context, then replay its key; both responses must contain the same order/items and stock must be decremented once. Cover the race-reload branch too.

### CA8. Concurrent payments with different keys can charge the same order twice — OPEN (High)
- **Where:** product-service `src/main/java/com/portcelana/natiart/service/AsaasPaymentService.java:138-176,206-228`, `service/PaymentIdempotencyService.java:27-41`, `model/Payment.java:19-29`.
- **Trigger / impact:** reservations serialize `(owner, Idempotency-Key)`, not the order. Two concurrent requests for the same order with different keys both acquire reservations, both see no payment, and both call Asaas. The unique `payment.orderId` constraint rejects the second local save only after two external charges exist. New keys are also generated when the optional header is omitted.
- **Fix:** reserve payment creation durably by order ID before provider egress; all client keys for that order must converge on the same payment attempt. Keep payload/owner checks and a defined state machine for replacement of a genuinely failed/cancelled attempt. Derive any provider idempotency value from this server-owned attempt, not solely an unscoped browser key. Do not rely on a post-charge unique constraint.
- **Acceptance:** synchronize two real transactions using different keys (and two requests with no key) for one order; exactly one provider create call occurs and both callers receive either the same payment or an explicit in-progress response. Different orders must remain independent.

### CA9. Order-less payment deduplication incorrectly treats null as a shared order ID — OPEN (Medium)
- **Where:** product-service `src/main/java/com/portcelana/natiart/service/AsaasPaymentService.java:121-136,158-166`; `repository/PaymentRepository.java:12`.
- **Trigger / impact:** the API still accepts missing `orderId`, but always calls `findByOrderIdAndOwnerExternalId(null, owner)`. Spring Data matches existing rows whose order ID is null. Parallel upload success followed by another upload failure or DB rollback also leaves orphan files, because filesystem writes are outside the database transaction. Multipart streams opened for dimension inspection/decoding are not explicitly closed, and storage closes only its output stream. The ten-new-image request cap does not cap retained existing images across repeated updates.
- **Fix:** give images stable owned resource records/keys and an explicit staged-to-committed lifecycle. Delete removed files after successful commit using retryable cleanup, clean failed staged uploads, and add an orphan reconciliation job with a grace period and reference checks. Define stream ownership and use try-with-resources for every opened input. Validate the combined retained/new image count and ownership before processing; coordinate ordering with CA26.
- **Acceptance:** failed conversion/upload/DB commit leaves no permanent unreferenced files; replacing/deleting releases only the removed unreferenced bytes after commit. Streams close on success/failure, repeated updates cannot grow an unlimited image list, and cleanup retries never delete an image still referenced by another record.

### CA57. Deactivated users and downgraded roles are still accepted by authentication — OPEN (High)
- **Where:** directory-service `service/AuthenticationManager.java` (`login`); `configuration/UserAuthenticationProvider.java` (`authenticateWithToken`); `model/User.java`; product token-validation cache.
- **Trigger / impact:** login checks only the password, and token authentication checks token expiry/issuer without enforcing `User.active`. Access-token authority comes from its old `roles` claim even though the current user/role is loaded from the database. An operator disabling a user or removing ADMIN in the database therefore does not reliably stop login or existing administrative access; the default access-token lifetime is 24 hours. There is currently no account-administration endpoint to coordinate revocation automatically.
- **Fix:** enforce the current account status and current effective role on login, refresh and token validation. Route account/role changes through a transactional service that revokes affected sessions and invalidates cached validation results under an explicit propagation contract. Define/remove unused role-active and user-type flags so their meaning is unambiguous. Keep generic external denial messages.
- **Acceptance:** issue an ADMIN token, disable or downgrade its account through the supported operation, and verify login/refresh/admin calls are rejected or downgraded across both services within the documented bound. The test must cover a warmed product-service cache and an otherwise unexpired token.

### CA58. Trusted-proxy rate limiting accepts an attacker-controlled first forwarded address — OPEN (Medium)
- **Where:** directory-service `configuration/RateLimitFilter.java` and product-service `configuration/ShippingRateLimitFilter.java` (`clientIp`); trusted-proxy deployment settings.
- **Trigger / impact:** when the immediate peer is trusted, both filters take the first `X-Forwarded-For` address. If that proxy appends the real client to an incoming header, a caller can choose a fresh first IP on every request and bypass the limit. This is conditional on the proxy/header policy; the default empty trust list ignores forwarded headers, but collapses all proxied users into one IP bucket instead. No tracked proxy configuration establishes the required overwrite behavior.
- **Fix:** define the deployment's trusted-hop model explicitly. Either configure the trusted edge to overwrite incoming forwarding headers and test that contract, or walk a parsed chain from the trusted right-hand side to the first untrusted hop. Normalize configured and received addresses consistently and share the parsing implementation/tests across services.
- **Acceptance:** with a trusted append-style proxy fixture, changing a forged leftmost address cannot reset the real client's quota. Different legitimate clients behind the documented proxy receive independent limits; untrusted direct peers cannot influence their key through headers.

### CA59. Correlation and provider error logs are incomplete and can retain raw personal data — OPEN (Medium)
- **Where:** both `RequestCorrelationFilter`/`PerformanceLoggingFilter` classes; directory `AsyncConfig`/`UserRegisteredEvent`/`AsaasUserManager`; product `AsaasPaymentService`/`ShippingService` error mapping; log configuration.
- **Trigger / impact:** request IDs are now forwarded on synchronous calls, so historical R1's claim of zero correlation is obsolete. However, async registration does not carry/copy the originating MDC, and normal lifecycle/error logs have no configured correlation field; a generated header alone does not correlate these records. All provider error mappers log the entire upstream body at WARN with no redaction, length cap or control-character handling. Such bodies can echo customer data or produce oversized/forged log lines.
- **Fix:** propagate a validated correlation ID explicitly in durable registration work (or a carefully cleared task decorator for the interim executor), include it in structured service logs and expose the response header where cross-origin clients need it. Log bounded provider error codes and safe identifiers, not raw customer/payment bodies. Add redaction and log-retention/access rules to the operational guide; keep sensitive detail out of browser telemetry.
- **Acceptance:** trace a signup through the actual async worker and an order/payment request across services using one visible request ID. Inject a provider error containing synthetic CPF/email, control characters and a large body: logs retain useful status/code context without those raw values or unbounded text.

### CA60. JWT interceptor attaches credentials to every origin except its third-party denylist — OPEN (Medium; exposure depends on a foreign HTTP caller)
- **Where:** `frontend/natiart-app/src/app/directory/interceptors/jwt-interceptor.service.ts` (`isExcludedDomain`, `jwtInterceptor`) and the spec named `does not exempt foreign origins that reuse an endpoint path`.
- **Trigger / impact:** an Angular HTTP request to `https://other.test/login` receives the access token; the current test explicitly expects this. A foreign 401 can also trigger refresh and receive the replacement access token on retry. Existing application callers target the two configured APIs and the excluded ViaCEP host, so this audit did not observe live exfiltration. The default credential policy nevertheless makes adding a third-party integration unsafe and uses a hostname suffix test without a label boundary.
- **Fix:** resolve request URLs against the actual application origin and attach/refresh credentials only for the explicitly configured directory/product API origins and base paths. Use exact parsed origin comparisons, including scheme/port; preserve legitimate relative API URLs and exempt auth endpoints within their configured base path. Remove the third-party denylist as the security boundary and avoid overwriting independently supplied third-party credentials.
- **Acceptance:** replace the foreign-origin token expectation with absence of both initial and refreshed credentials. Cover arbitrary foreign origins, protocol-relative URLs, lookalike host suffixes, non-default ports, configured API path prefixes and relative requests. A foreign 401 must cause no directory refresh, token mutation or login navigation.

### CA61. Purchased orders have no customer recovery or administrator fulfillment workflow — OPEN (Medium; feature gap)
- **Where:** product-service `controller/OrderController.java`, `service/OrderManagerImpl.java` (`getAllOrders`, `getOrderById`), `model/CustomerOrderItem.java`, `dto/OrderItemDto.java`; frontend order service, routes and checkout/PIX components.
- **Trigger / impact:** the controller exposes only order creation. A buyer who closes the PIX tab cannot list or reopen their purchases, and an administrator cannot progress fulfillment through the application. The latent read methods are unbounded/owner-unaware and return entities with lazy associations, so exposing them directly would create data disclosure and serialization problems. Order lines preserve price/quantity but rely on a mutable product reference for product identity details; later catalog edits can change the description of what was purchased.
- **Fix:** agree the minimum order-history and fulfillment screens, then implement owner-scoped paginated customer reads and separately authorized admin reads/commands. Map DTOs inside transactions with explicit fetch plans; never expose the current unrestricted methods directly. Snapshot the purchased label/SKU and accepted customization/shipping details at creation, retain history when products are retired, and expose only owned payment-resume information. Coordinate payment/status/reservation changes with CA11–CA16 and use server-confirmed state in the UI.
- **Acceptance:** a buyer can reopen a pending payment and inspect a paid order after reload; another buyer cannot list/read it by guessing IDs. An admin can perform only allowed fulfillment transitions. Catalog edits do not rewrite purchase history, list queries are bounded, and responses serialize after the persistence context closes.

### CA62. Loop health and audit cadence can report progress without completed work — OPEN (Medium)
- **Where:** `scripts/loop-watchdog-check.sh` (`fetch_prs`, `loop_active_count`); `scripts/loop-cycle.sh` (`SLOT`, red-team condition, cycle prompt and health row); `scripts/run-agent.sh` model-skip fallback; `scripts/agent-models.conf`.
- **Trigger / impact:** the watchdog treats any recent update on generic `fix/`/`docs/`/other matching PR branches as loop activity, including human comments or human-owned branches, and misses healthy audit-only cycles that create no PR. Red-team work runs only when a process reaches exactly `SLOT % 480 == 0`; sleeping/offline hosts can repeatedly miss it. Reviewer independence compares CLI/model labels even though the config explicitly identifies two Muse entries as the same weights, and an exhausted skip pool silently permits the excluded model. Exit zero and a self-reported model footer do not prove completion or an independent review.
- **Fix:** emit an authenticated, bounded completion heartbeat containing cycle ID, reviewed commit, outcome and artifacts, and have the watchdog distinguish no work, successful audit, failed attempt and host inactivity. Track the last successful lens/red-team completion so missed work is performed on a later run. Assign a canonical model-family ID independently of gateway labels; enforce independence for automatic approval, or explicitly require manual review when no independent model is available. Do not treat unrelated PR activity or a runner exit code as the deliverable.
- **Acceptance:** human comments cannot mask a stopped loop; a documented successful audit without a PR counts as progress. Simulate missed time slots and verify overdue red-team work runs once on recovery. Same-model aliases and skip exhaustion cannot produce an automatically accepted "independent" review.

### CA63. Unused payment and utility dependencies increase maintenance without supporting a live feature — OPEN (Low)
- **Where:** `frontend/natiart-app/package.json` (`@adyen/adyen-web`); root agent-guide mirrors claiming Adyen payments; `backend/product-service/build.gradle.kts` (`org.apache.poi:poi`); `storage/StorageFileSystem.java` and its unused ZIP overload.
- **Trigger / impact:** no storefront source imports Adyen; the working provider integration is server-side Asaas/PIX, while card submission is unimplemented (CA32). Apache POI is imported only for stream copying and temporary files, bringing an office-document library into an image-storage service. Dead ZIP/reset helpers and duplicated service infrastructure make future maintenance harder to scope. This is dependency/install and comprehension overhead, not evidence that the unused Adyen module is included in the shipped JavaScript bundle or that these versions have a known vulnerability.
- **Fix:** remove the unused Adyen dependency until the card-provider decision is made and update the mirrored overview together. Replace POI's utility calls with JDK stream/file primitives, preserving close/delete semantics and ZIP tests, then remove POI if the complete reference scan is empty. Remove unreachable helpers opportunistically. Extract shared infrastructure only where both services already have the same stable contract; avoid a broad framework rewrite or merging distinct domain models merely because names match.
- **Acceptance:** lockfile/Gradle graphs no longer include the removed direct dependencies solely through these declarations; production builds and storage behavior remain correct. Documentation identifies the actually supported payment flow, and no unused helper is exposed just to justify keeping it.

### CA64. Storefront metadata and language defaults do not describe the shop or its products — OPEN (Low; design/discoverability)
- **Where:** `frontend/natiart-app/src/index.html`, route configuration, product-detail component and public favicon; storefront templates and locale providers.
- **Trigger / impact:** every route starts with the internal title `NatiArtFrontend`, there is no description or product-specific share metadata, and there is no route title/meta management. The app uses English text/default locale while checkout requires Brazilian CEP/CPF and BRL/PIX, without an explicit audience/language choice. Shared product links therefore provide little useful identity and localized shoppers see inconsistent conventions. Full mobile layout and assistive-technology behavior were not verified in a browser during this audit.
- **Fix:** choose the supported initial locale with the owner; configure consistent language, BRL/date/number formatting and translated labels as needed. Set a shop title/description/icon and product route titles/descriptions; provide server-rendered or prerendered public product metadata if share previews/search indexing are required. Keep private checkout/account data out of public metadata and use only real product claims/assets.
- **Acceptance:** public shop/product links expose distinct accurate metadata and a recognizable shop icon; prices and form instructions follow the chosen locale consistently. Confirm representative narrow/wide layouts and keyboard/screen-reader purchase navigation in the rendered application alongside CA34.

### CA65. Public storefront assets include personal academic documents unrelated to the shop — OPEN (High; privacy)
- **Where:** `frontend/natiart-app/src/assets/img/a2.jpg` and `a3.jpg`; `product/components/customer/dashboard/top-banner/top-banner.component.ts` image list; `directory/components/auth/signup/signup.component.html:8`; `angular.json` build assets; generated `dist/nati-art-frontend/browser/assets/img/`.
- **Trigger / impact:** visual inspection identifies a personal certificate and detailed academic record containing identifying information. The homepage carousel lists both images and signup directly renders the academic record with the inaccurate alt text "Elegant porcelain". Angular also copies them into production assets, making direct retrieval possible. `a4.jpg` is unrelated placeholder imagery in the carousel. This confirms source/build exposure and intended rendering, not whether a particular public deployment currently serves these bytes.
- **Fix:** replace the personal documents and unrelated carousel fixture with approved shop imagery and correct their references/alt text; keep any necessary test fixture synthetic and outside the build asset glob. Redeploy cleaned assets and invalidate/remove old published copies according to the deployment's retention rules. Ask the repository owner to decide whether Git-history removal is also needed; do not rewrite shared history automatically. Add a small explicit asset inventory/review check so arbitrary personal files cannot silently enter the public bundle.
- **Acceptance:** a clean production build contains only approved storefront assets; the removed URLs return 404 in the deployed version and are absent from retained public release directories/caches under the operator's control. Preserve no copied personal details in tests, logs or this audit.

### CA66. Missing stored images are reported as server failures — OPEN (Low)
- **Where:** product-service `storage/StorageFileSystem.java` (`openFile`, `resolveAllowedFile`), `service/ProductManagerImpl.java` (`getProductImage`) and `controller/ProductController.java` (`getProductImage`).
- **Trigger / impact:** an image URI can pass root confinement but point to a missing file. `openFile` wraps the resulting I/O exception in `IllegalStateException`, which becomes a generic 500. A removed upload, broken persisted reference or guessed missing key therefore looks like a server outage, produces noisy error logs and gives the client no stable missing-image contract. Successful images already have seven-day public caching; absence of cache headers is not the issue.
- **Fix:** translate missing/non-file resources to a static 404 at the storage boundary while preserving real disk/permission failures as operational errors. Return no physical path in public error messages. Use the stable resource-key contract from CA48/CA56 and ensure the frontend displays an existing fallback asset once instead of retrying a missing placeholder.
- **Acceptance:** missing file, directory path and forbidden-root requests return the documented safe denial without absolute-path disclosure; a real disk I/O failure remains observable as an operational error. Existing valid image bytes, media type and cache behavior remain correct.

### CA67. Required customer accounts have no usable password-recovery flow — OPEN (Medium; feature gap)
- **Where:** directory-service `service/PasswordManager.java` (`notifyResetPassword`, `doResetPassword`), token/registration controllers; frontend login and account routes.
- **Trigger / impact:** checkout requires an account, but login offers no password recovery and no controller connects reset-token issuance/redemption to a notification channel. `notifyResetPassword` is an empty TODO. A returning customer who forgets the password cannot regain access through the application. Existing reset helpers are latent implementation pieces, not a complete feature, and should not be exposed as public endpoints unchanged.
- **Fix:** implement a bounded request/reset flow with a uniform request response, verified delivery to the account address, short-lived single-use reset tokens and atomic redemption. Validate both password fields before dereferencing, apply the same password policy as registration, revoke old sessions/cache entries on success, and never put usable reset tokens in logs or telemetry. Add accessible request/new-password screens and recovery guidance; coordinate session invalidation with CA57.
- **Acceptance:** a synthetic notification fixture delivers one valid reset link; expired, reused, concurrent and wrong-purpose tokens cannot reset a password. Unknown/existing usernames get the same external request response, throttling applies, a successful reset revokes prior sessions, and the buyer can log in and resume their owned order.

## Deferred decisions retained from earlier audits

### B9. Cache-miss directory latency remains a service dependency — DEFERRED (Low)
- **Where / why:** product `configuration/JwtAuthFilter.java` now uses a shared bounded validation cache, a singleton client and a five-second timeout. The old claim of a remote call on every request is fixed. Cache misses still block a servlet thread on directory availability, and public reads can wait before degrading to anonymous.
- **Decision / fix:** measure cache misses, authentication latency and outage behavior before choosing a different verification architecture. If necessary, use local signature validation with a documented revocation contract or another bounded service design; do not add negative caching without analyzing authorization semantics. CA2/CA3/CA57 remain current fixes.
- **Acceptance if adopted:** load/outage tests show the agreed latency and revocation bounds for both cached and uncached sessions, with protected operations failing closed.

### K5. Cleanup jobs repeat across replicas — DEFERRED (Low)
- **Where / why:** directory `service/TokenCleanupService.java` and database cleanup schedulers execute per instance. Idempotent deletion is currently safe; duplicate database work may matter at larger scale.
- **Decision / fix:** measure query cost/lock contention before introducing shared scheduling. If needed, use a database lease or a documented singleton job with bounded batches and restart recovery.
- **Acceptance if adopted:** multiple replicas clean expired state without concurrent expensive scans or loss of live sessions; failed job ownership can recover.

### T5. Dependency verification and scanning policy is incomplete — DEFERRED (Low)
- **Where / why:** Gradle builds/wrapper properties have no complete dependency lock/checksum verification setup; CI has no dependency/container audit gate. GitHub Actions are now SHA-pinned (historical AL2 is fixed), and current npm audit is clean. Container tags still float.
- **Decision / fix:** agree supported artifact registries, checksum/lock review, base-image digest refresh, vulnerability thresholds and exceptions. Then add Gradle verification/locking, wrapper distribution checksums, dependency/container scanning and reproducible artifact provenance to CI without automatically blocking on unreviewed tool output.
- **Acceptance if adopted:** unexpected artifacts/checksum drift fail before build execution, an intentional update has a reviewable lock/verification diff, and a synthetic disallowed advisory exercises the chosen gate without revealing credentials.

### L3. Guest checkout is a product decision — DEFERRED (Low)
- **Where / why:** checkout is authenticated; the old ghost-registration endpoint and ghost checkout path have been removed. The old account-hijack/enumeration descriptions are not current implementation tasks.
- **Decision / fix:** retain required accounts or design guest purchase/resume with explicit ownership proof. Never restore the old email-only token-issuing endpoint. Coordinate any guest design with CA5/CA13/CA61 and existing-account recovery (CA67).
- **Acceptance if adopted:** guests can prove ownership to resume purchases, and presenting another person's email alone grants no account/session/order access.

### BG1. Multi-tab/device cart reconciliation is undefined — DEFERRED (Low)
- **Where / why:** frontend `product/service/cart.service.ts` stores one local snapshot and does not consume storage events or synchronize with the server-cart API. Independent tabs can overwrite each other's saved edits; signing in on another device does not restore the browser cart.
- **Decision / fix:** specify browser-only versus account-backed cart behavior and conflict/merge rules before adding synchronization. Reuse a versioned line/personalization contract with CA13/CA21; do not blindly merge quantities or another account's draft.
- **Acceptance if adopted:** two tabs/devices and logout/login as another account follow the documented merge/isolation rules, with stable line identity and no silent loss of confirmed edits.

### BD3. ZIP helpers need limits if they become externally reachable — DEFERRED (Low)
- **Where / why:** product `storage/StorageFileSystem.java` (`downloadFiles`, `downloadDirectory`) has no request caller. Archive size/file-count/depth limits are absent, and temporary archive cleanup on build failure needs attention. This is a latent helper concern, not a current anonymous ZIP endpoint.
- **Decision / fix:** remove unused helpers as part of CA63 or add explicit size/count/depth/time limits and failure cleanup before exposing an export feature. Preserve path confinement, symlink handling and unique entry names.
- **Acceptance if adopted:** oversized/deep inputs terminate within configured bounds, failed export leaves no temporary archive, and links cannot export bytes outside allowed roots.
